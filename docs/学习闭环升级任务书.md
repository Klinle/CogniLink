## 一、任务概述

### 1.1 目标

将 ROADMAP 中的三个里程碑合并为一次持续交付的升级任务，围绕产品定位——**把你上传的教材，变成可对话、可练习、可追踪的私人 CS 教练**——补齐学习闭环的右半段（巩固、复习、计划），并深化练习与检索体验。

### 1.2 范围

- **M1 补齐学习闭环**: T1 诊断式 Onboarding、T2 错题本与间隔重复、T3 引用溯源跳转
- **M2 练习与检索深化**: T4 会话内出题、T5 Pyodide 代码沙箱、T6 检索质量看板
- **M3 扩展场景**: T7 学习路径规划器、T8 教师班级空间、T9 PWA 移动端
- **功能池**: 12 项补充功能（F1–F12），按依赖关系随里程碑择机排入

### 1.3 不在范围

- 泛聊天能力增强（与通用 AI 助手重复的建设不做）
- 多租户 SaaS 化、计费系统
- 前端整体重构（数据层迁移 react-query 作为横切工程项并行推进，不阻塞功能）

### 1.4 成功指标

| 类别 | 指标 | 目标 |
|------|------|------|
| 闭环 | 新用户完成诊断率 | ≥ 70% |
| 闭环 | 周复习队列完成率 | ≥ 50% |
| 信任 | 带溯源回答占 RAG 回答比例 | ≥ 90%，点击率可观测 |
| 练习 | code 题沙箱客观判分覆盖率 | ≥ 95%（沙箱可用时） |
| 质量 | 检索零结果率 | 可观测且逐周下降 |
| 工程 | 后端测试 | 每个 T 交付时 pytest 全绿 |

## 二、里程碑 M1 —— 补齐学习闭环

### T1 诊断式 Onboarding

**目标**: 解决新用户空状态与画像冷启动——首次登录三步向导：选目标领域 → 上传教材或选用内置知识库 → 10 题诊断测验初始化画像。

| 层 | 改动 |
|----|------|
| 数据库 | `users` 增 `onboarding_completed INTEGER DEFAULT 0`；`labs` 增 `tag VARCHAR(30)`（`diagnostic` 标记诊断题，按 6 领域预置各 10 题，可用 [external_ai_lab_generation_guide.md](./external_ai_lab_generation_guide.md) 流程批量生成） |
| 后端 | `GET /api/onboarding/status`；`POST /api/onboarding/complete`；`POST /api/onboarding/diagnose`（接收答卷 → 按领域正确率写入 `user_knowledge_states.proficiency` 初值，正确率 ≥ 0.8 的节点直接点亮） |
| 前端 | 新页 `/onboarding` 三步向导（复用 exercise-renderer 渲染诊断题）；登录后 `onboarding_completed=0` 时由 dashboard 重定向；支持"跳过，稍后再说" |
| 验收 | 新注册用户首登进入向导；完成后 `/profile` 雷达图非全零；跳过后 dashboard 常驻入口可补做 |

依赖: 无。规模: 中。

### T2 错题本与间隔重复

**目标**: 答错的题自动进入复习队列，按遗忘曲线调度每日复习，形成"练习 → 巩固"闭环。

| 层 | 改动 |
|----|------|
| 数据库 | 新表 `user_review_items`：`id, user_id FK, source_type(lab/dynamic/collection), lab_id FK nullable, content JSON(题目快照), answer JSON, wrong_count, ease_factor FLOAT DEFAULT 2.5, interval_days INTEGER DEFAULT 0, due_at, last_reviewed_at, state(new/learning/review/graduated), created_at`；索引 `(user_id, due_at)` |
| 后端 | 新 `review_service`：SM-2 简化调度（答题质量 0–5 → 更新 ease/interval/due；连续 3 次高质量作答毕业出队）；入队钩子挂在 `POST /api/labs/{id}/submit` 与 `/api/labs/evaluate-dynamic` 的失败分支（按题目去重）。API：`GET /api/reviews/today`、`POST /api/reviews/{id}/answer`、`GET /api/reviews/stats`、`DELETE /api/reviews/{id}` |
| 前端 | dashboard 增"今日待复习 N 题"卡片；新页 `/review` 逐题复习（复用 exercise-renderer），答完展示间隔变化 |
| 验收 | 答错自动入队且不重复；复习答对间隔按算法拉长；毕业出队；统计接口返回近 7/30 日完成率 |

依赖: 无（T4/T5 产生的错题后续自动接入）。规模: 大。此表起点引入 Alembic 管理迁移（见 §六）。

### T3 引用溯源跳转

**目标**: 回答中的 `[来源: 文档, 第N页]` 从纯文本变为可点击跳转，强化"基于你的教材回答"的信任感。

| 层 | 改动 |
|----|------|
| 后端 | `rag_service._format_chunks` 同步返回结构化来源列表；`graph_service.run_stream` 在 `rag_bot done` 事件 `data.sources` 中携带 `[{document_id, title, page_number, chunk_id}]`（content 流不变，保持兼容） |
| 前端 | `use-chat` 把 `sources` 挂到当前 assistant 消息；消息底部渲染来源 chip；点击打开文档预览弹层并定位页码（PDF 走 `/{id}/file` iframe `#page=N`，文本走 `/{id}/content` 分页参数） |
| 验收 | 命中知识库的回答显示来源 chip；点击 3 秒内看到对应页内容；无命中时不显示 |

依赖: 无。规模: 小。建议 M1 内最先交付。

## 三、里程碑 M2 —— 练习与检索深化

### T4 会话内出题

**目标**: 对话中说"给我出两道装饰器的题"即在聊天流内出现互动练习卡片，做完即评测——把"理解"与"练习"无缝衔接。RAG 流水线意图树已能识别 `practice_request`，本任务是其消费方。

| 层 | 改动 |
|----|------|
| 后端 | `graph_service.run_stream` 对 `intent=practice_request` 分支：解析目标知识点（LLM 从 rewritten_query 提取节点名 → 匹配 `knowledge_nodes`，无匹配时取用户最弱节点），调用 `evaluation_service.generate_targeted_exercise`，以新 SSE 事件 `event: exercise` 输出题目 JSON（含 exercise_type/test_cases/detailed_explanation） |
| 前端 | `use-chat` 处理 `exercise` 事件 → 聊天流内渲染 exercise-renderer 卡片；提交走既有 `POST /api/labs/evaluate-dynamic`；答错自动进 T2 复习队列 |
| 验收 | 练习请求不再返回纯文本题目而是互动卡片；提交即时评分与解析；错题入队 |

依赖: T2（错题入队）。规模: 中。

### T5 Pyodide 代码沙箱

**目标**: code 题在浏览器 WASM 内真实执行测试用例，客观判分 + LLM 讲解，评测准确性与 local-first 双收益。

| 层 | 改动 |
|----|------|
| 前端 | 自托管 Pyodide 资源（`public/pyodide/`，不依赖 CDN）；Web Worker 执行用户代码 + `test_cases.sample_io` 断言，超时 5s 熔断；结果与 LLM 讲解（既有评测接口）合成展示 |
| 后端 | `evaluate-dynamic` / `submit` 增可选入参 `sandbox_result`，评分策略：沙箱通过率占 70%，LLM 代码质量分占 30%；沙箱缺席时回退纯 LLM 评测（现状） |
| 验收 | 断网状态下 code 题仍可判对错；恶意代码（死循环）被 Worker 超时终止不影响页面 |

依赖: 无。规模: 大（前端为主）。注意 Pyodide 体积约 10MB，需懒加载 + 首次加载提示。

### T6 检索质量看板

**目标**: 让 RAG 流水线的效果可观测，指导知识库补充，也是流水线迭代的回归工具。

| 层 | 改动 |
|----|------|
| 数据库 | 新表 `retrieval_logs`：`id, user_id, query, rewritten_query, sub_queries JSON, intent, domain, rag_hit INTEGER, context_chars INTEGER, tool_hit INTEGER, created_at`；索引 `(created_at)` |
| 后端 | `run_stream` 阶段 5 结束后异步落库（`asyncio.create_task`，失败不影响主流程）；`GET /api/admin/retrieval-stats`（近 7/30 日命中率、零结果查询 TopN、领域分布、意图分布） |
| 前端 | `/admin` 新增"检索质量"标签页：命中率趋势、零结果查询列表（一键复制去补充知识库） |
| 验收 | 管理员可见命中率趋势与零结果 TopN；日志写入不增加对话可感知延迟 |

依赖: 无。规模: 中。

## 四、里程碑 M3 —— 扩展场景

### T7 学习路径规划器

**目标**: 输入目标（领域 + 期限），基于图谱先修关系生成每日学习计划，与练习联动。

| 层 | 改动 |
|----|------|
| 数据库 | 新表 `user_learning_plans`：`id, user_id, goal_domain, target_days, plan JSON([{day, node_ids, status}]), started_at, status(active/completed/abandoned)` |
| 后端 | `POST /api/knowledge/plan`（对目标领域节点做先修拓扑排序，跳过已点亮节点，按天均分；扩展既有 `knowledge_service` recommend 逻辑）；`GET /api/knowledge/plan/current`；节点点亮时自动更新计划进度，逾期未完成顺延 |
| 前端 | dashboard "今日计划"卡片（节点直达 `/graph` 与 `/practice`）；`/graph` 页高亮计划路径 |
| 验收 | 生成 N 天计划且先修顺序正确；完成节点自动打勾；中途放弃可重建 |

依赖: 无（与 T2 复习队列在 dashboard 并列展示）。规模: 中。

### T8 教师班级空间

**目标**: 把教师角色从 mock 变真：建班、邀请入班、布置作业、查看学情。

| 层 | 改动 |
|----|------|
| 数据库 | 新表 `classes`：`id, name, teacher_id FK, invite_code UNIQUE, created_at`；`class_members`：`class_id FK, user_id FK, joined_at, UNIQUE(class_id, user_id)`；`assignments`：`id, class_id FK, title, lab_ids JSON, due_at, created_at` |
| 后端 | 教师端 CRUD（`/api/classes`），学生凭邀请码入班（`POST /api/classes/join`）；作业完成度基于 `user_lab_submissions` 聚合；`admin/students` 页数据源替换为真实班级成员学情（复用 `profile_service` 聚合） |
| 前端 | 教师端 `/admin/classes`（建班/邀请码/作业布置/完成率矩阵）；学生端 dashboard 显示所属班级与待完成作业 |
| 验收 | 邀请码入班全流程可用；教师看到每个学生的作业完成率与薄弱领域；权限隔离（学生不可见他人明细，教师仅见本班） |

依赖: T2/T7 交付后学情维度更完整（非硬依赖）。规模: 大。

### T9 PWA 移动端

**目标**: 复习是碎片化场景，移动端可安装、核心路径可离线。

| 层 | 改动 |
|----|------|
| 前端 | `manifest.json` + Service Worker（next-pwa 或手写）；静态资源缓存；`/review` 页数据预取实现离线复习（答题结果回线后同步）；对 dashboard/review/practice 做移动端响应式核查 |
| 验收 | Lighthouse PWA 可安装项通过；手机端完成"看今日复习 → 答题 → 看解析"全流程；断网进入 `/review` 可复习已预取题目 |

依赖: T2。规模: 中。

## 八、执行顺序与依赖

```
工程项(CI/Alembic/锁定) ──┐
T3 溯源跳转(小) ──────────┤
T2 错题+间隔复习 ─────────┼─→ T4 会话内出题 ─→ F1 闪卡 / F2 面试
T1 诊断 Onboarding ───────┤
                          ├─→ T5 沙箱(独立并行)
                          ├─→ T6 检索看板(独立并行)
                          └─→ T7 计划 → T9 PWA → F7/F9
                               T8 班级(独立，靠后)
```

建议单周节奏：每周交付 1 个 T（T2/T5/T8 各留 2 周），每个 T 交付即含 pytest 用例与验收核对，里程碑收口做一次整体回归 + 检索看板数据核验。

## 九、风险清单

| 风险 | 影响 | 缓解 |
|------|------|------|
| LLM 出题/判分质量不稳定 | T1 诊断失真、T4 体验差 | 诊断题走人工预置题库；动态题保留 detailed_explanation 人工抽检通道（admin 已有题库管理） |
| Pyodide 体积与兼容性 | 首屏变慢、部分浏览器不可用 | 自托管 + Worker 懒加载 + 纯 LLM 评测降级路径 |
| SM-2 参数不适配题型 | 复习节奏过密/过疏 | 参数配置化（memory_settings 模式的 per-user 设置表），先默认后调优 |
| 班级权限模型引入越权面 | 数据泄露 | 沿用 get_current_user 依赖链新增 get_class_teacher 校验；T8 交付必含权限专项测试（参照 test_api_security.py 模式） |
| 新表未走 Alembic 导致漂移 | 环境不一致 | §六 工程项前置，T2 起强制 |
| 检索日志膨胀 | 存储与查询变慢 | retrieval_logs 保留 90 天，定期清理任务 |
